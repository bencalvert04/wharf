# Wharf in Slack

This is a single-workspace, allowlisted-conversation demo integration. It uses Anthropic to interpret scheduling requests by default. With `SLACK_INTERPRETER=jev`, Typesafe Jev makes the scheduling interpretation, while Anthropic may word short replies. Wharf's authenticated meeting APIs handle availability and Google Calendar booking; calendar data and meeting credentials are never passed to either model provider. The selected interpreter receives scheduling text, relevant bounded conversation context, timestamps, the scheduling timezone, and current date. Text can contain Slack identifiers; the Anthropic interpreter also receives the background author identifiers.

## Setup

1. Create a Slack app from `docs/slack-manifest.json` in the intended workspace. If Slack requires the event URL to be verified before credentials exist, omit `event_subscriptions` initially and add it after step 4.
2. Install the scopes in the manifest, including channels:read and channels:history for channel naming and recent context. Invite the bot into the Wharf channel. Email access is not required.
3. Configure server-only Vercel production variables: SLACK_SIGNING_SECRET, SLACK_BOT_TOKEN, SLACK_TEAM_ID, SLACK_CHANNEL_ID, ANTHROPIC_API_KEY, SLACK_AGENT_MODEL. The default Anthropic model is claude-haiku-5-5. To use Jev, set SLACK_INTERPRETER=jev and TYPESAFE_API_KEY; TYPESAFE_MODEL defaults to jev-latest. ANTHROPIC_API_KEY is still required for short replies in Jev mode. Set provider spending limits for the demo. Never infer production provider selection from `.env.example` or the presence of a key: verify the nonsecret selector in the deployment configuration. Existing DATABASE_URL and GOOGLE_TOKEN_ENCRYPTION_KEY must remain configured.
4. Run the database migration and deploy. Set Events Request URL to https://wharfmeetings.com/api/slack/events, subscribe to app_mention, and set Interactivity URL to https://wharfmeetings.com/api/slack/interactions. Use one canonical callback host even if Wharf has two domains.

## Demo

Mention the bot: `@Wharf schedule 30 minutes with @Ray next week`. Use real Slack mentions, not typed display names. The requester is always included. If details are missing, repeat the full request with the clarification. Start each new meeting in a new thread.

The bot creates a meeting through the same service used by the public meeting API for the conversation’s participant roster, then posts a shared join link. People with saved calendar connections may be joined automatically; others receive a private connection prompt. Details inferred from older messages need requester confirmation before creation. When everyone has joined, the bot can suggest a time; only the organizer can confirm booking and authorize Google Calendar invitations. Older open-join meetings retain their original join behavior.

An explicit requested meeting name takes priority. Otherwise channel meetings use the channel name and group DMs use human attendee names. Recent history supplies clearly relevant missing details: up to 15 human messages from the last seven days, bounded to 6,000 characters. Thread replies are read where Slack permits them; channel history and saved clarifications remain available otherwise. History reads run in parallel with metadata/database work, share a 1.5-second deadline, and skip retries. Current explicit details override background. Background is not stored in the clarification record.
The bot does not continuously poll calendars. For reserved-roster meetings, it performs an on-demand primary-calendar free/busy refresh and suggests the earliest shared time when all calendars are connected; a separate organizer confirmation is required to book. Explicit find-and-book requests also refresh availability before selecting a new time. It cannot access calendars until participants join and cannot bypass Google's unverified-app flow. Google guest settings can prevent invitations from appearing automatically.

## Reliability and costs

Slack signatures, timestamps, workspace and channel restrictions are enforced. Durable database jobs deduplicate event deliveries and use a three-minute processing lease. Work runs through Next.js `after` with a 120-second maximum. Failed steps show a retry message; user buttons allow recovery. A process terminated by the hosting platform may require another mention or button click. Delivery to Slack is at-least-once, so a crash after a channel message is sent can produce a duplicate message, but meeting creation and calendar booking are idempotent.

The default Anthropic interpreter has a 700 output-token ceiling, up to 12,000 characters of request/follow-up text and 6,000 characters of older conversation context. In Jev mode, up to 12 request/context entries are considered (each human request capped at 4,000 characters); the history reader retains the same 15-message/seven-day/6,000-character limit. Jev receives up to 12 parseable history entries. Optional Anthropic short replies have a 100 output-token ceiling and receive at most 2,000 characters of message text, not calendar data. A daily workspace limit of 100 incoming scheduling mentions bounds normal demo usage. No automatic model upgrade or fallback to a more expensive model. Slack job payloads are removed after success; a daily cleanup removes records older than 30 days. Meeting bearer keys are encrypted at rest using the existing token vault with separate associated-data labels.

## Validation

Run `npm test`, `npm run typecheck`, and `npm run build`. Before recording, test in the configured channel with two accounts: automatic creation, shared channel invitation, both joins, organizer consent, slot confirmation, duplicate click, and a click from someone other than the requester. Live provider tests require separately approved real interactions, installed Slack credentials, and funded access to the selected providers.

Group DMs: configure SLACK_GROUP_CHANNEL_IDS (comma-separated allowlist) and SLACK_BOT_USER_ID. Install mpim:history and mpim:read and subscribe to message.mpim. Only explicit bot mentions trigger responses; normal conversation is ignored. Conversation membership supplies DM naming and the participant roster; saved calendar connections can be reused and missing connections receive private prompts. Before creation, up to 12 context entries in the same requester’s thread (including requester messages and Wharf clarification prompts), plus any proposed meeting details, are saved to resolve clarification. Context is eligible for reuse for one day after its last update; the daily cleanup removes expired records. Background history is not saved in this clarification record. Existing meetings remain immutable; requests to change them receive guidance to start a new message. In the default Anthropic mode, greetings and status commands use deterministic intent checks; Jev mode classifies them with Jev and may use Anthropic for a short reply. No automatic retry worker is configured.
