# Calendar providers

The Link calendar dialog offers Google Calendar, Outlook Calendar, and iCloud Calendar. A person without a Google account can connect Outlook or iCloud directly. The header login uses the same picker. Saved connections are reused when joining another meeting; disconnect removes saved credentials without deleting meeting snapshots.

## Before enabling

1. Run `npm run db:migrate` against the target database as part of the release. This adds `calendar_provider_connections` and `calendar_provider_states`; existing Google tables and identity values are preserved. Legacy columns called `google_sub` are account keys: new standalone identities use `microsoft:` or `icloud:` namespaces. Do not interpret all such values as Google subjects.
2. Keep `GOOGLE_TOKEN_ENCRYPTION_KEY` configured and stable within each environment. Never rotate or replace the existing production key as part of this setup. The existing vault encrypts all provider credentials using account-bound AES-GCM. Never put credentials in client variables, source control, or logs.
3. Register a Microsoft Entra application allowing **accounts in any organizational directory and personal Microsoft accounts**. Add a **Web** callback: `https://wharfmeetings.com/api/auth/microsoft/callback` (and the exact local APP_URL equivalent for testing). Set server-only `MICROSOFT_CLIENT_ID` and `MICROSOFT_CLIENT_SECRET`. Request delegated `User.Read`, `Calendars.ReadBasic`, and `offline_access`; organizational policy may require administrator approval. No calendar write permission is requested. The Outlook button reports Setup required until configured.
4. iCloud uses CalDAV and does not require a shared Apple application secret. Each user needs two-factor authentication and their own app-specific password generated at https://account.apple.com/. This is **not** Sign in with Apple. Never ask for a normal Apple Account password. iCloud is unavailable until the server token vault is configured.
5. Keep `INVITATION_FROM` and `GMAIL_APP_PASSWORD` configured for non-Google planners. Without an email sender, finalization fails before saving a time. Google planners keep the native Google event invitation flow. Non-Google planners use the existing transactional calendar email outbox (with its existing ambiguous-delivery review behavior). No live test messages are sent automatically.

## Data and permissions

Google still requests primary-calendar free/busy. Outlook's basic read permission is broader, but calendarView uses an explicit select of start/end/showAs/isCancelled; no subject, body, location, or attendees are requested. calendarView supports both personal and organizational accounts and expands recurrences server-side. Every page must load successfully before any snapshot is saved. Tentative, busy, out-of-office, and unknown states block time; free and cancelled events do not.

iCloud credentials allow wider access than free/busy, including writes. The server transport allows only read methods and restricts requests and redirects to Apple's CalDAV hosts. CalDAV reads all accessible event calendars within the meeting window, asks Apple to expand recurrence, and derives busy intervals; calendar content is not persisted. Transparent and cancelled events are excluded. All-day dates use the calendar's IANA timezone, falling back to the meeting timezone when absent. Unsupported or malformed calendar responses fail rather than claim the person is free. Floating timed events (without UTC or a recognized IANA timezone) and unrecognized event timezones are currently unsupported; reconnecting does not fix these calendar-data limitations. All active server-expanded occurrences with the same UID are included.

Disconnecting deletes local Microsoft/iCloud credentials. The user should additionally revoke Microsoft consent or the Apple app-specific password in provider settings. Google disconnection retains its existing provider revocation behavior. If an external connection was attached to a Google Wharf identity that still has a Google grant, Disconnect also invokes that Google revoke/delete flow. Connections are not merged across independently signed-in provider identities. When an already signed-in Wharf user links Outlook or iCloud, it is attached to that existing Wharf identity; the existing invitation email and display name are retained. Linking Google onto a standalone Microsoft/iCloud identity is not supported: sign out before using a separate Google identity. Signing out does not transfer existing memberships or invitation claims.

The website and saved availability refresh support all three providers. A failed provider read never inserts an empty/free snapshot, and an agent refresh failure aborts that refresh before any snapshot update. Existing snapshots are retained, however. Ordinary website finalization (including Slack’s web-choice path) still validates the last saved snapshots rather than automatically reading every live calendar; a previous failed refresh does not persist a booking-blocking failure flag. This snapshot behavior predates these integrations and is not a promise that every booking path checks live availability. The Slack bot's direct attendance/organizer authorization entry points remain Google-specific; this change does not advertise full Outlook/iCloud Slack booking support. No direct Microsoft/iCloud event writes are implemented.

## Validation before release

Run the build and tests, migrate a staging database, then test with consenting real accounts: personal Outlook, Microsoft 365 (including any admin-consent restrictions), and iCloud. Test first connection, declined consent, rejoin, sign out/in, disconnect/reconnect, mixed-provider availability, DST and all-day events, and finalization email acceptance. Provider mocks validate code paths, but cannot replace these account tests. The original implementation handoff reported checking Microsoft app registration/delegated permissions, a token-endpoint credential check, and migrating a supplied test database. Those environment-specific claims are not established by the code or mocked tests and must be verified separately for the intended environment. The handoff also reported a BYU administrator-consent request; no delegated calendar access was confirmed. A real delegated Outlook connection, iCloud connection, and mixed-provider invitation test still need to be completed before release.

References: [Microsoft calendarView](https://learn.microsoft.com/en-us/graph/api/calendar-list-calendarview?view=graph-rest-1.0), [Microsoft OAuth code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow), [Apple app-specific passwords](https://support.apple.com/en-us/102654).


## Safe isolated staging checklist

Configuration, not the application code, establishes environment isolation. Obtain explicit approval before credential configuration, real-account authorization, migrations, invitations, or deployment.

- Use a separate, empty staging database with a verified staging-only `DATABASE_URL`. Never copy production sessions, calendar grants, tokens, invitation outbox jobs, or user data into it. Do not run migrations against production during staging setup; the production October 27 connection-generation migration is a separate, already-applied change.
- Give staging its own `GOOGLE_TOKEN_ENCRYPTION_KEY`, stable for that staging environment. Do not copy, regenerate, rotate, or otherwise change the production key. Do not use the production database with a new key.
- Set the exact staging `APP_URL` and register matching Google and Microsoft callbacks (`APP_URL/api/auth/google/callback` and `APP_URL/api/auth/microsoft/callback`) through an approved secure configuration path. Preserve existing production Google configuration unchanged. Never paste secrets into source, PR comments, logs, or documentation.
- Run mocked tests with no production Google/Microsoft credentials, Gmail sender password, Slack credentials, or real user app-specific passwords. The unit tests use mocked provider transport and in-memory PostgreSQL; `npm test`, `npm run typecheck`, and `npm run build` do not require a live calendar or database. Do not run the environment-loading verification, email, or migration scripts as part of this offline check.
- Only after separate authorization, use consenting staging test accounts for first connection, denial, rejoin, sign-out/in, disconnect/reconnect, concurrent provider switching, DST/all-day/expanded recurrences, and mixed-provider invitations. Use an approved test email sender and recipients. Verify both provider acceptance and actual invitation receipt/acceptance; mocked outbox tests prove neither.
- Keep the PR draft and the feature undeployed until that real-account evidence and all required approvals are recorded. BYU administrator approval and personal Outlook/iCloud access are separate prerequisites, not test passes.


## Concurrent provider-switch limitation

The Google return flow checks the captured external connection generation and current session before writing a snapshot, and deletes only the captured generation. Regression tests cover a newer provider completing during Google token exchange or availability reads, and standalone non-Google accounts are blocked from silently switching identity through Google linking. These checks are not a shared transactional user-intent sequence: the generation check, session update, and snapshot write are separate database statements. A switch in the final check/write interval is not fully serialized. Treat simultaneous multi-tab/provider switching as a remaining rollout risk requiring further transactional design and interleaving tests; do not describe the partial guard as complete race safety.
