# Calendar providers

The Link calendar dialog offers Google Calendar and Outlook Calendar. The header login also offers official Sign in with Apple when configured. Apple sign-in authenticates a Wharf account only; it does not connect iCloud Calendar. The former Apple password form and password submission handler are disabled. Saved connections are reused when joining another meeting; disconnect removes saved credentials without deleting meeting snapshots.

## Before enabling

1. Run `npm run db:migrate` against the target database as part of the release. This adds `calendar_provider_connections`, `calendar_provider_states`, and the additive intent protocol in `db/calendar-intent-schema.mjs`; existing Google grants and identity values are preserved. The intent protocol adds a session sequence, intent fields to OAuth states, a shared sequence, hashed account markers, and guarded SQL functions. Do not deploy the application before this schema is applied through the separately authorized release process. Legacy columns called `google_sub` are account keys: new standalone identities use `microsoft:` or `icloud:` namespaces. Do not interpret all such values as Google subjects.
2. Keep `GOOGLE_TOKEN_ENCRYPTION_KEY` configured and stable within each environment. Never rotate or replace the existing production key as part of this setup. The existing vault encrypts all provider credentials using account-bound AES-GCM. Never put credentials in client variables, source control, or logs.
3. Register a Microsoft Entra application allowing **accounts in any organizational directory and personal Microsoft accounts**. Add a **Web** callback: `https://wharfmeetings.com/api/auth/microsoft/callback` (and the exact local APP_URL equivalent for testing). Set server-only `MICROSOFT_CLIENT_ID` and `MICROSOFT_CLIENT_SECRET`. Request delegated `User.Read`, `Calendars.Read`, and `offline_access`; organizational policy may require administrator approval. No calendar write permission is requested. The Outlook button reports Setup required until configured.
4. For official Apple sign-in, follow [the Apple sign-in setup record](apple-signin.md). Do not collect Apple passwords. The retained CalDAV implementation is no longer offered for new connections.
5. Keep `INVITATION_FROM` and `GMAIL_APP_PASSWORD` configured for non-Google planners. Without an email sender, finalization fails before saving a time. Google planners keep the native Google event invitation flow. Non-Google planners use the existing transactional calendar email outbox (with its existing ambiguous-delivery review behavior). No live test messages are sent automatically.

## Data and permissions

Google still requests primary-calendar free/busy. Outlook's delegated calendar-read permission is broader, but calendarView uses an explicit select of start/end/showAs/isCancelled; no subject, body, location, or attendees are requested. calendarView supports both personal and organizational accounts and expands recurrences server-side. Every page must load successfully before any snapshot is saved. Tentative, busy, out-of-office, and unknown states block time; free and cancelled events do not.

Wharf now consistently requests delegated `Calendars.Read`, the read-only permission validated with the consenting personal Outlook account. The former staging-only compatibility flag is obsolete and ignored. `ReadBasic` was advertised as sufficient by Microsoft, but returned 403 for this account with the same query; this change adopts the successfully tested permission rather than claiming that Microsoft's narrower permission is generally unsupported. Existing ReadBasic-only grants must reconnect and approve the new scope. Token exchanges and refreshes lacking explicit `Calendars.Read` are rejected before any calendar read. This scope can authorize more event data than Wharf fetches; the minimal select remains unchanged and no calendar-write scope is requested. Tenant administrator restrictions still apply. See [the live Microsoft evidence](microsoft-staging.md).

iCloud credentials allow wider access than free/busy, including writes. The server transport allows only read methods and restricts requests and redirects to Apple's CalDAV hosts. CalDAV reads all accessible event calendars within the meeting window, asks Apple to expand recurrence, and derives busy intervals; calendar content is not persisted. Transparent and cancelled events are excluded. All-day dates use the calendar's IANA timezone, falling back to the meeting timezone when absent. Unsupported or malformed calendar responses fail rather than claim the person is free. Floating timed events (without UTC or a recognized IANA timezone) and unrecognized event timezones are currently unsupported; reconnecting does not fix these calendar-data limitations. All active server-expanded occurrences with the same UID are included.

Disconnecting deletes local Microsoft/iCloud credentials. The user should additionally revoke Microsoft consent or the Apple app-specific password in provider settings. Google disconnection retains its existing provider revocation behavior. If an external connection was attached to a Google Wharf identity that still has a Google grant, Disconnect also invokes that Google revoke/delete flow. Connections are not merged across independently signed-in provider identities. When an already signed-in Wharf user links Outlook or iCloud, it is attached to that existing Wharf identity; the existing invitation email and display name are retained. Linking Google onto a standalone Microsoft/iCloud identity is not supported: sign out before using a separate Google identity. Signing out does not transfer existing memberships or invitation claims.

The website and saved availability refresh support all three providers. A failed provider read never inserts an empty/free snapshot, and an agent refresh failure aborts that refresh before any snapshot update. Existing snapshots are retained, however. Ordinary website finalization (including Slack’s web-choice path) still validates the last saved snapshots rather than automatically reading every live calendar; a previous failed refresh does not persist a booking-blocking failure flag. This snapshot behavior predates these integrations and is not a promise that every booking path checks live availability. The Slack bot's direct attendance/organizer authorization entry points remain Google-specific; this change does not advertise full Outlook/iCloud Slack booking support. No direct Microsoft/iCloud event writes are implemented.

## Concurrent provider changes and rollout

Each calendar action carries a durable, monotonically ordered session intent and account markers. Account markers use a domain-separated SHA-256 hash of the account identifier plus a sequence; they contain no provider credentials, raw account identifiers, profile fields, or busy intervals. Markers persist across connection deletion so an older callback cannot recreate access after disconnect. Every operation has a database-issued ten-minute deadline, rechecked after acquiring the lock in every guarded transaction; binding a verified identity never extends that deadline. Markers become eligible for deletion fifteen minutes after their latest protected activity (and at least five minutes after any captured deadline). Cleanup runs under the same lock, opportunistically on new actions and through the existing daily cleanup job. Deletion is not guaranteed at exactly fifteen minutes: inactive markers remain until a successful cleanup. Expired intents cannot revive after marker deletion or recreation. This is separate from deleting credential-bearing Google/Microsoft/iCloud connection records and from session/meeting retention.

The server checks the captured intent inside the same database transaction as each protected statement (or explicit batch), under one short transaction-scoped advisory lock. Provider network requests happen outside that lock. A newer sign-in, provider switch, disconnect, or same-session sign-out invalidates older protected writes; late-discovered OAuth identities cannot supersede a newer account action. Account-wide refresh captures all participant markers and checks the whole vector with the final snapshot/revision update, so one stale participant aborts that update. Existing per-connection UUID checks remain as additional protection.

This orders protected database effects; it is not a distributed transaction with Google, Microsoft, Apple, SMTP, or Slack. An already-started provider request cannot be undone, and operations may have completed earlier valid database steps before a newer action supersedes later work. Previously saved snapshots remain subject to the snapshot-only booking limitations above. A single short global database lock favors correctness for the current small application; monitor contention before scaling rather than moving network requests inside a transaction.

Release prerequisites:

- Apply the additive intent schema first, only to an explicitly approved target. No live migration was performed by this review. Isolated PGlite tests exercise schema and protocol behavior, not the target Neon database or real provider accounts.
- Reject pending OAuth states without a captured intent; users restart those connections. Existing encrypted grants and the stable encryption key remain unchanged.
- Do not run old unguarded and new guarded auth handlers concurrently against the same database. Drain or disable old auth/connection traffic during rollout, including old deployment URLs if still reachable. Rollback to unguarded handlers requires the same precaution; keep the additive schema and use only the guarded expiry cleanup for account markers.
- Verify complete real-account sign-in/denial/rejoin/disconnect and mixed-invitation flows in isolated staging, including simultaneous tabs/sessions and provider failures, before release. Neither green unit tests nor the code review authorizes migration, deployment, or calendar invitations.

These tests exercise real PostgreSQL semantics in isolated PGlite and mocked provider transport, but do not establish multi-process Neon advisory-lock contention, live provider behavior, or deployment readiness.

## Retry and failure verification

`npm test` exercises the actual finalization handler with real isolated PostgreSQL state, discarded success responses, concurrent repeated confirmations, overlapping delivery workers, SMTP-response loss, database acknowledgment loss, abandoned leases, and transaction rollback. Google recovery is also tested with a real local HTTP socket reset after a simulated provider commits the event. These provider failures are controlled fault injection, not induced failures at Google or Gmail.

The opt-in staging database check runs the actual finalization/delivery store functions against disposable tables in the approved Neon staging database:

```sh
env -u DATABASE_URL -u APP_URL node --env-file=.env.staging.local --experimental-strip-types scripts/verify-invitation-retries.mjs
```

It refuses any other database hostname or app URL, sends no email or calendar traffic, checks concurrent transactions and ambiguous outcomes, and removes its test schema in `finally`. Real participant tables and invitation jobs are not used. Successful retry checks do not guarantee provider uptime. SMTP has no idempotency key: an ambiguous attempt remains for operator review and is never automatically resent, even after its lease expires.
